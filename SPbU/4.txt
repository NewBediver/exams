# 1. Командные оболочки и языки сценариев

## 1.1. Понятие командной оболочки

**Командная оболочка**, или *shell*, — системная программа, которая предоставляет пользователю и другим программам интерфейс для запуска команд и управления вычислительной средой.

Типичный цикл работы оболочки:

1. прочитать командную строку или строку сценария;
2. разбить её на слова и операторы;
3. выполнить подстановки переменных, команд и шаблонов;
4. провести синтаксический анализ;
5. настроить перенаправления ввода-вывода;
6. выполнить встроенную команду либо запустить внешнюю программу;
7. дождаться завершения или организовать фоновое выполнение;
8. получить статус завершения.

POSIX определяет shell как интерпретатор командного языка, который выполняет лексический и синтаксический разбор, подстановки, перенаправления и запуск команд. ([pubs.opengroup.org](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html?utm_source=openai))

Следует различать:

- **терминал** — средство ввода и отображения вывода;
- **командную оболочку** — интерпретатор команд;
- **ядро ОС** — компонент, управляющий процессами, памятью и устройствами;
- **команду** — встроенную операцию оболочки или отдельную программу.

Графический терминал может запускать Bash, PowerShell или другую оболочку. Сама оболочка не является ядром операционной системы.



## 1.2. Встроенные и внешние команды

Команда оболочки может быть:

### Встроенной

Выполняется внутри процесса оболочки:

```sh
cd /tmp
export PATH
read name
```

Например, `cd` должна быть встроенной: внешняя программа не может изменить текущий каталог родительского процесса оболочки.

### Внешней

Оболочка находит исполняемый файл и запускает новый процесс:

```sh
grep pattern file.txt
find . -name '*.c'
```

### Функцией оболочки

```sh
say_hello()
{
    printf 'Hello, %s\n' "$1"
}
```

### Псевдонимом

```sh
alias ll='ls -l'
```

### Составной конструкцией

К ним относятся циклы, условия, группы команд и подпрограммы языка оболочки.



## 1.3. Среда выполнения

Каждый процесс получает:

- аргументы командной строки;
- переменные окружения;
- текущий каталог;
- стандартные потоки;
- права доступа;
- идентификаторы пользователя и группы;
- ограничения ресурсов.

Переменная `PATH` содержит каталоги, в которых оболочка ищет внешние команды.

```sh
PATH=/usr/local/bin:/usr/bin:/bin
```

Переменная оболочки не обязательно передаётся дочерним процессам. Для включения в окружение применяется `export`:

```sh
LANG=ru_RU.UTF-8
export LANG
```

или:

```sh
export LANG=ru_RU.UTF-8
```



## 1.4. Стандартные потоки и файловые дескрипторы

В Unix-подобной системе процесс обычно получает:

| Дескриптор | Поток |
|:||
| 0 | стандартный ввод, `stdin` |
| 1 | стандартный вывод, `stdout` |
| 2 | стандартный поток ошибок, `stderr` |

Перенаправление:

```sh
command < input.txt
command > output.txt
command >> output.txt
command 2> errors.txt
command > output.txt 2>&1
```

Разделение обычного вывода и сообщений об ошибках позволяет независимо обрабатывать результаты программы и диагностику.



## 1.5. Конвейеры

Конвейер связывает стандартный вывод одной команды со стандартным вводом другой:

```sh
command1 | command2 | command3
```

Пример:

```sh
ps -ef | grep server | sort
```

Каждая программа выполняет отдельную операцию:

1. `ps` формирует список процессов;
2. `grep` выбирает нужные строки;
3. `sort` сортирует результат.

В традиционных Unix-оболочках между процессами передаётся поток байтов, обычно интерпретируемый как текст. В PowerShell по конвейеру между командлетами передаются объекты со свойствами и типами. ([learn.microsoft.com](https://learn.microsoft.com/en-gb/powershell/module/microsoft.powershell.core/about/about_pipelines?view=powershell-7.4&utm_source=openai))



## 1.6. Unix-подобные командные оболочки

Основные семейства:

- Bourne shell — `sh`;
- POSIX shell;
- Bash;
- Korn shell — `ksh`;
- Z shell — `zsh`;
- C shell — `csh`, `tcsh`;
- Fish.

`sh` и совместимые оболочки широко используются в:

- Linux и Unix;
- системных сценариях;
- загрузочных процедурах;
- контейнерах;
- CI/CD;
- административной автоматизации.

### Переменные

```sh
name='Alice'
printf '%s\n' "$name"
```

Пробелы вокруг `=` при обычном присваивании недопустимы:

```sh
name = Alice    # это не присваивание
```

### Позиционные параметры

- `$0` — имя сценария;
- `$1`, `$2`, … — аргументы;
- `$#` — число аргументов;
- `"$@"` — все аргументы с сохранением их границ;
- `$?` — статус предыдущей команды;
- `$$` — идентификатор процесса оболочки.

### Подстановка команд

```sh
current_date=$(date)
```

### Арифметика

```sh
count=$((count + 1))
```

### Шаблоны файлов

```sh
*.txt
file?.c
[0-9]*
```

Это **шаблоны оболочки**, или glob-паттерны, а не регулярные выражения.



## 1.7. Кавычки

### Одинарные кавычки

```sh
'$HOME'
```

Содержимое рассматривается буквально.

### Двойные кавычки

```sh
"$HOME"
```

Выполняется подстановка переменных и команд, но результат сохраняется как один аргумент.

### Экранирование

```sh
\$
\*
```

Типичная безопасная конструкция:

```sh
rm -- "$file"
```

Без кавычек:

```sh
rm $file
```

значение переменной может разделиться на несколько аргументов или подвергнуться раскрытию шаблонов.



## 1.8. Управляющие конструкции shell

### Условный оператор

```sh
if [ -f "$file" ]; then
    printf 'Regular file\n'
elif [ -d "$file" ]; then
    printf 'Directory\n'
else
    printf 'Not found\n'
fi
```

### Цикл

```sh
for file in "$@"; do
    printf '%s\n' "$file"
done
```

```sh
while read -r line; do
    printf '%s\n' "$line"
done < input.txt
```

### Выбор

```sh
case "$answer" in
    yes|y) printf 'Accepted\n' ;;
    no|n)  printf 'Rejected\n' ;;
    *)     printf 'Unknown answer\n' ;;
esac
```

### Условное выполнение

```sh
compile && run_tests
compile || report_error
```

Команда после `&&` выполняется при успешном завершении предыдущей, после `||` — при неуспешном.



## 1.9. Пример shell-сценария

```sh
#!/bin/sh

if [ "$#" -ne 1 ]; then
    printf 'Usage: %s directory\n' "$0" >&2
    exit 2
fi

directory=$1

find "$directory" -type f -name '*.log' -print
```

Сценарий проверяет число аргументов, сохраняет имя каталога и ищет журнальные файлы.

Статус `0` обычно означает успех, ненулевой статус — ошибку или специальный отрицательный результат в соответствии с соглашениями программы.



## 1.10. Фоновые процессы и задания

Фоновый запуск:

```sh
long_task &
```

Команды управления заданиями:

```sh
jobs
fg
bg
```

Оболочка может:

- создавать процессы;
- объединять их конвейерами;
- ожидать завершения;
- посылать сигналы;
- переводить процессы в фон;
- передавать терминал выбранной группе процессов.

Команда:

```sh
exec program argument
```

не создаёт новый процесс, а заменяет текущий процесс оболочки указанной программой.



## 1.11. Command shell Windows

Классическая оболочка Windows — `cmd.exe`. Её сценарии имеют расширения `.bat` или `.cmd`.

Пример:

```bat
@echo off
setlocal

if "%~1"=="" (
    echo Usage: script directory
    exit /b 2
)

for %%F in ("%~1\*.txt") do (
    echo %%F
)

endlocal
```

Основные средства:

- `set NAME=value` — присваивание;
- `%NAME%` — значение переменной;
- `%1`, `%2` — параметры;
- `%ERRORLEVEL%` — код завершения;
- `if` — условие;
- `for` — цикл;
- `call` — вызов сценария или подпрограммы;
- `goto` — переход;
- `setlocal/endlocal` — локализация изменений;
- `|`, `>`, `>>`, `2>` — конвейеры и перенаправления.

Современная Windows предоставляет две основные оболочки: классическую Command shell и PowerShell; для развитой автоматизации Microsoft рекомендует PowerShell. ([learn.microsoft.com](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/windows-commands))



## 1.12. PowerShell

PowerShell — командная оболочка, язык сценариев и платформа автоматизации. Современный PowerShell работает не только в Windows, но также в Linux и macOS. ([learn.microsoft.com](https://learn.microsoft.com/en-us/powershell/scripting/overview?view=powershell-7.5))

Команды часто именуются по схеме «глагол — существительное»:

```powershell
Get-Process
Get-ChildItem
Stop-Process
```

### Объектный конвейер

```powershell
Get-Process |
    Where-Object CPU -gt 10 |
    Sort-Object CPU -Descending |
    Select-Object Name, CPU
```

Передаются объекты процессов, поэтому следующая команда обращается к их свойствам, а не разбирает текстовое представление.

### Переменные

```powershell
$name = "Alice"
$numbers = @(1, 2, 3)

$config = @{
    Host = "server"
    Port = 8080
}
```

### Условия и циклы

```powershell
if (Test-Path $path) {
    Get-Item $path
}

foreach ($file in Get-ChildItem *.txt) {
    Write-Output $file.FullName
}
```

### Исключения

```powershell
try {
    Get-Content $path -ErrorAction Stop
}
catch {
    Write-Error $_
}
finally {
    Write-Output "Completed"
}
```

Сценарии PowerShell имеют расширение `.ps1`, а повторно используемые функции могут объединяться в модули. ([learn.microsoft.com](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_scripts?view=powershell-7.6&utm_source=openai))



## 1.13. Сравнение оболочек

| Свойство | POSIX shell/Bash | `cmd.exe` | PowerShell |
|||||
| Основной конвейер | поток байтов/текста | текст | объекты |
| Сценарии | `.sh` | `.bat`, `.cmd` | `.ps1` |
| Переменная | `$name` | `%name%` | `$name` |
| Обработка ошибок | статусы, `trap` | `ERRORLEVEL` | статусы и исключения |
| Структуры данных | строки, в Bash — массивы | ограниченные | объекты, массивы, словари |
| Модули | функции, подключаемые файлы | пакетные подпрограммы | полноценные модули |
| Основная среда | Unix/Linux | Windows | кроссплатформенная |

# 2. Инструменты `find`, `grep`, `sed`

## 2.1. Общий принцип

Классический Unix-подход состоит в создании небольших программ, каждая из которых выполняет одну функцию:

- `find` выбирает объекты файловой системы;
- `grep` выбирает строки по шаблону;
- `sed` преобразует поток текста.

Сложная обработка строится композицией:

```sh
find ... | grep ... | sed ...
```



## 2.2. Команда `find`

Общая форма:

```sh
find начальные_каталоги выражение
```

Например:

```sh
find /usr/src -type f -name '*.c' -size +100k -print
```

`find` рекурсивно обходит дерево каталогов и вычисляет выражение отдельно для каждого найденного объекта. Если начальная точка не указана, GNU `find` использует текущий каталог; при отсутствии выражения применяется действие `-print`. ([gnu.org](https://www.gnu.org/software/findutils/find))

### Поиск по имени

```sh
find . -name '*.txt'
```

Шаблон следует заключать в кавычки, иначе `*.txt` может быть раскрыт оболочкой до запуска `find`.

`-name` применяет glob-шаблон, а не регулярное выражение.

В GNU `find` поиск без учёта регистра:

```sh
find . -iname '*.jpg'
```

### Поиск по типу

```sh
find . -type f    # обычные файлы
find . -type d    # каталоги
find . -type l    # символические ссылки
```

### По размеру

```sh
find . -type f -size +10M
find . -type f -size -1k
```

### По времени изменения

```sh
find . -type f -mtime +7
find . -type f -mmin -30
```

### По владельцу и правам

```sh
find /home -user alice
find . -type f -perm -004
```



## 2.3. Логические выражения `find`

Логическое И:

```sh
find . -type f -name '*.c'
```

Логическое И обычно подразумевается между соседними условиями.

Логическое ИЛИ:

```sh
find . -type f \( -name '*.c' -o -name '*.h' \)
```

Отрицание:

```sh
find . -type f ! -name '*.bak'
```

Скобки экранируются, поскольку имеют специальное значение для оболочки.

Важно понимать, что `find` возвращает нулевой статус при успешном обходе, даже если ни одного объекта не найдено. Ненулевой статус обычно означает ошибку самого обхода или выполнения действий. ([gnu.org](https://www.gnu.org/software/findutils/find))



## 2.4. Действия `find`

### Вывод имени

```sh
find . -type f -print
```

### Запуск программы для каждого файла

```sh
find . -type f -name '*.c' \
    -exec grep -nH 'TODO' {} \;
```

`{}` заменяется именем текущего файла.

### Пакетная передача нескольких файлов

```sh
find . -type f -name '*.c' \
    -exec grep -nH 'TODO' {} +
```

Форма с `+` передаёт одной команде максимально допустимое число имён и обычно эффективнее запуска отдельного процесса для каждого файла. ([gnu.org](https://www.gnu.org/software/findutils/manual/html_node/find_html/Multiple-Files.html?utm_source=openai))

### Удаление

```sh
find cache -type f -mtime +30 -delete
```

Перед удалением выражение следует проверить:

```sh
find cache -type f -mtime +30 -print
```



## 2.5. Безопасная обработка имён файлов

Имена файлов Unix могут содержать:

- пробелы;
- табуляции;
- кавычки;
- обратные косые черты;
- переводы строк.

Поэтому небезопасна конструкция:

```sh
for file in $(find . -type f); do
    ...
done
```

Результат командной подстановки будет разделён оболочкой на слова.

Безопасные варианты:

```sh
find . -type f -exec command {} +
```

или:

```sh
find . -type f -print0 |
    xargs -0 command
```

`-print0` завершает каждое имя нулевым байтом, который не может входить в имя файла; `xargs -0` использует тот же разделитель. Эта связка предназначена для корректной обработки произвольных имён. ([gnu.org](https://www.gnu.org/software/findutils/manual/html_node/find_html/Safe-File-Name-Handling.html?utm_source=openai))



## 2.6. Команда `grep`

`grep` выбирает строки, соответствующие шаблону.

```sh
grep [параметры] шаблон файлы
```

Примеры:

```sh
grep 'error' application.log
grep -i 'error' application.log
grep -n 'error' application.log
grep -v 'debug' application.log
```

Основные параметры:

| Параметр | Назначение |
|||
| `-i` | не учитывать регистр |
| `-v` | выбрать несовпадающие строки |
| `-n` | показать номера строк |
| `-c` | показать число выбранных строк |
| `-l` | вывести имена файлов с совпадением |
| `-L` | вывести имена файлов без совпадения |
| `-r` | рекурсивный поиск |
| `-w` | совпадение целого слова |
| `-x` | совпадение целой строки |
| `-q` | не выводить строки, использовать только статус |
| `-A n` | показать \(n\) строк после совпадения |
| `-B n` | показать \(n\) строк до совпадения |
| `-C n` | показать контекст с двух сторон |
| `-o` | вывести только совпавший фрагмент |

Опции `-w` и `-x` соответственно ограничивают совпадение целым словом и целой строкой. ([gnu.org](https://www.gnu.org/s/grep/manual/html_node/Matching-Control.html?utm_source=openai))



## 2.7. Регулярные выражения `grep`

### Базовые регулярные выражения

Применяются по умолчанию:

```sh
grep '^Error' file
grep 'end$' file
grep '[0-9][0-9]*' file
```

### Расширенные регулярные выражения

```sh
grep -E 'error|warning' file
grep -E '^[A-Za-z_][A-Za-z0-9_]*$' file
```

### Фиксированная строка

```sh
grep -F 'a[b]' file
```

В режиме `-F` специальные символы регулярных выражений рассматриваются буквально.

Шаблоны рекомендуется заключать в кавычки, чтобы метасимволы не интерпретировались оболочкой.



## 2.8. Статусы `grep`

Обычно:

- `0` — найдена хотя бы одна выбранная строка;
- `1` — совпадений нет;
- `2` — произошла ошибка.

Следовательно, отсутствие совпадения — не техническая ошибка:

```sh
if grep -q 'ready' status.txt; then
    echo 'Service is ready'
else
    status=$?

    if [ "$status" -eq 1 ]; then
        echo 'Service is not ready'
    else
        echo 'Cannot search the file' >&2
    fi
fi
```

Различение отсутствия совпадения и ошибки существенно при написании надёжных сценариев. ([gnu.org](https://www.gnu.org/software/grep/manual/html_node/?utm_source=openai))



## 2.9. Команда `sed`

`sed` — потоковый редактор, применяющий программу преобразований к последовательности строк.

Общая форма:

```sh
sed [параметры] 'программа' файлы
```

Замена первого совпадения в каждой строке:

```sh
sed 's/old/new/' file.txt
```

Замена всех совпадений:

```sh
sed 's/old/new/g' file.txt
```

По умолчанию исходный файл не изменяется: результат поступает в стандартный вывод.



## 2.10. Цикл работы `sed`

`sed` поддерживает два основных буфера:

- **пространство шаблона**, pattern space;
- **удерживающее пространство**, hold space.

Стандартный цикл:

1. прочитать строку в pattern space;
2. выполнить над ней команды;
3. вывести pattern space, если автоматический вывод не отключён;
4. перейти к следующей строке.

Hold space сохраняет данные между циклами и используется при сложной многострочной обработке. ([gnu.org](https://www.gnu.org/software/sed/manual/sed.html?utm_source=openai))



## 2.11. Основные команды `sed`

### Замена

```sh
sed 's/cat/dog/g' file
```

### Вывод выбранных строк

```sh
sed -n '10,20p' file
```

`-n` отключает автоматический вывод, а `p` явно печатает выбранные строки.

### Удаление строк

```sh
sed '/^[[:space:]]*#/d' file
```

Удаление пустых строк:

```sh
sed '/^[[:space:]]*$/d' file
```

### Обработка диапазона

```sh
sed '/BEGIN/,/END/p' file
```

### Изменение только выбранных строк

```sh
sed '/error/s/^/[ERROR] /' file
```

### Завершение после строки

```sh
sed '100q' file
```

Синтаксис основной команды замены имеет вид:

```text
s/регулярное_выражение/замена/флаги
```

Флаг `g` означает замену всех совпадений в pattern space. ([gnu.org](https://www.gnu.org/software/sed/manual/sed.html?utm_source=openai))



## 2.12. Совместное применение

Найти исходные файлы с `TODO`:

```sh
find src -type f \( -name '*.c' -o -name '*.h' \) \
    -exec grep -nH 'TODO' {} +
```

Выбрать ошибки и удалить временную метку:

```sh
grep 'ERROR' application.log |
    sed 's/^[0-9-]* [0-9:]* //'
```

Найти Java-файлы, содержащие `Deprecated`:

```sh
find . -type f -name '*.java' \
    -exec grep -l 'Deprecated' {} +
```

Итоговое различие:

- `find` ищет **файлы**;
- `grep` ищет **строки или фрагменты текста**;
- `sed` выполняет **потоковые преобразования текста**.

# 3. Системы программирования и модульное программирование

## 3.1. Понятие системы программирования

**Система программирования** — комплекс языковых, программных и информационных средств, обеспечивающий создание, преобразование, выполнение, тестирование и сопровождение программ.

Типичный состав:

1. язык программирования;
2. текстовый редактор или IDE;
3. препроцессор;
4. компилятор или интерпретатор;
5. ассемблер;
6. редактор связей;
7. загрузчик;
8. отладчик;
9. библиотеки;
10. система сборки;
11. профилировщик;
12. средства тестирования;
13. документация.



## 3.2. Инструментальная цепочка

```text
исходная программа
        ↓
препроцессор
        ↓
компилятор
        ↓
ассемблер
        ↓
объектный модуль
        ↓
редактор связей
        ↓
исполняемый файл
        ↓
загрузчик
        ↓
процесс
```

В типичной системе C/C++ компиляция концептуально включает препроцессирование, собственно компиляцию, ассемблирование и связывание. Драйвер компилятора может запускать эти стадии автоматически или останавливаться после выбранной стадии. ([gcc.gnu.org](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html?utm_source=openai))



## 3.3. Язык и транслятор

Язык программирования задаёт:

- лексику и синтаксис;
- типы;
- правила областей видимости;
- семантику операций;
- модель памяти;
- механизмы модулей;
- правила обработки ошибок.

**Транслятор** преобразует программу с одного языка на другой.

Виды трансляторов:

- компилятор;
- ассемблер;
- препроцессор;
- транспилятор;
- генератор кода.

**Интерпретатор** непосредственно выполняет исходную программу или её промежуточное представление. Компиляция и интерпретация могут сочетаться, например при выполнении байт-кода с JIT-компиляцией.



## 3.4. Объектный модуль

После компиляции обычно формируется перемещаемый объектный файл, содержащий:

- машинный код;
- статические данные;
- секции;
- таблицу определённых символов;
- ссылки на внешние символы;
- записи перемещения;
- отладочную информацию.

Например, объектный модуль может определять функцию `calculate`, но содержать неразрешённую ссылку на `print_result`.



## 3.5. Редактор связей

**Редактор связей**, или компоновщик, объединяет объектные модули и библиотеки.

Основные функции:

1. объединить секции;
2. найти определения внешних символов;
3. выбрать нужные модули из библиотек;
4. назначить адреса кода и данных;
5. выполнить перемещения;
6. сформировать исполняемый файл или библиотеку.

GNU `ld`, например, объединяет объектные и архивные файлы, размещает их секции и разрешает символьные ссылки. ([sourceware.org](https://sourceware.org/binutils/docs/ld.html?utm_source=openai))

### Разрешение символов

```text
module_a:
    undefined print_result

module_b:
    defined print_result
```

Компоновщик связывает ссылку из `module_a` с определением в `module_b`.

Типичные ошибки:

- неопределённый внешний символ;
- несколько несовместимых определений;
- отсутствующая библиотека;
- несовпадение соглашений вызова;
- несовместимый формат объектных файлов.



## 3.6. Статическое и динамическое связывание

### Статическое

Нужный код библиотеки включается в исполняемый файл.

Преимущества:

- меньше внешних зависимостей;
- предсказуемая версия;
- простота распространения.

Недостатки:

- увеличение размера файла;
- дублирование библиотечного кода;
- обновление требует повторной компоновки.

### Динамическое

Библиотека загружается отдельно при старте программы или по требованию.

Преимущества:

- совместное использование кода процессами;
- меньшие исполняемые файлы;
- возможность независимого обновления.

Недостатки:

- необходимость совместимой версии;
- ошибки поиска библиотеки;
- зависимость от бинарного интерфейса.



## 3.7. Загрузчик

Загрузчик операционной системы:

1. создаёт виртуальное адресное пространство;
2. отображает сегменты программы;
3. подключает динамические библиотеки;
4. выполняет необходимые динамические перемещения;
5. создаёт стек и окружение;
6. передаёт управление точке входа.

Следует различать:

- **компоновку** — построение программы;
- **загрузку** — создание процесса для её выполнения.



## 3.8. Текстовый редактор и IDE

Текстовый редактор обеспечивает:

- ввод и изменение текста;
- поиск и замену;
- навигацию;
- подсветку синтаксиса;
- запуск внешних команд.

IDE дополнительно интегрирует:

- компилятор;
- систему сборки;
- отладчик;
- анализатор кода;
- рефакторинг;
- тестирование;
- управление проектом;
- средства контроля версий.

IDE не заменяет отдельные стадии инструментальной цепочки, а предоставляет над ними объединённый интерфейс.



## 3.9. Отладчик

Отладчик позволяет:

- запускать и останавливать программу;
- выполнять её пошагово;
- устанавливать точки останова;
- просматривать стек вызовов;
- исследовать переменные и регистры;
- изменять значения;
- устанавливать точки наблюдения;
- перехватывать исключения и сигналы;
- анализировать аварийные дампы.

Виды контрольных точек:

- **breakpoint** — остановка при достижении строки, функции или адреса;
- **watchpoint** — остановка при изменении выражения или области памяти;
- **catchpoint** — остановка при событии, например исключении или загрузке библиотеки. ([sourceware.org](https://www.sourceware.org/gdb/download/onlinedocs/gdb.html/Breakpoints.html?utm_source=openai))



## 3.10. Модульное программирование

**Модульное программирование** — организация программы как системы относительно независимых компонентов с явно определёнными интерфейсами.

Модуль имеет:

- имя;
- интерфейс;
- реализацию;
- экспортируемые сущности;
- скрытые детали;
- зависимости;
- правила инициализации;
- иногда собственное состояние.

Основные принципы:

1. декомпозиция;
2. сокрытие информации;
3. явные интерфейсы;
4. высокая внутренняя связность;
5. слабое сцепление;
6. раздельная компиляция;
7. повторное использование;
8. независимое тестирование.



## 3.11. Типы модулей

### Исходный модуль

Файл с исходным текстом:

```text
parser.c
network.java
module.py
```

### Интерфейсный модуль

Описание доступных внешних сущностей:

```text
parser.h
module interface
package specification
```

### Единица компиляции

Часть программы, независимо обрабатываемая компилятором.

### Объектный модуль

Результат отдельной компиляции.

### Библиотечный модуль

Компонент статической или динамической библиотеки.

### Загрузочный модуль

Исполняемый файл или загружаемый компонент.

### Пакет

Совокупность логически связанных модулей с метаданными и версией.

### Плагин

Модуль, подключаемый во время выполнения через интерфейс расширения.

### Компонент или служба

Относительно самостоятельная, иногда отдельно развёртываемая часть системы.



## 3.12. Связывание модулей по управлению

Под связыванием по управлению понимается передача исполнения между модулями:

- вызов функции;
- вызов метода;
- обратный вызов;
- возбуждение исключения;
- событие;
- передача сообщения;
- удалённый вызов;
- запуск процесса.

На машинном уровне вызов требует соглашения о:

- передаче параметров;
- возвращении результата;
- размещении данных в регистрах и стеке;
- сохранении регистров;
- представлении типов;
- обработке исключений;
- именовании символов.

Совокупность таких правил образует **ABI**, двоичный интерфейс приложений.



## 3.13. Связывание модулей по данным

Обмен данными выполняется посредством:

1. параметров;
2. возвращаемых значений;
3. общих глобальных переменных;
4. разделяемых структур;
5. файлов;
6. базы данных;
7. разделяемой памяти;
8. каналов и сокетов;
9. очередей сообщений;
10. сериализованных запросов и ответов.

Предпочтителен обмен через явно определённый интерфейс: он позволяет контролировать типы, владение, инварианты и обработку ошибок.



## 3.14. Виды сцепления

От более слабого к более сильному:

### Сцепление по данным

Передаются только необходимые значения:

```text
calculate(price, count)
```

### Сцепление по структуре

Передаётся крупный объект, из которого используется только часть.

### Сцепление по управлению

Один модуль передаёт другому флаг, определяющий его внутренний алгоритм:

```text
process(data, mode=3)
```

### Сцепление через общую область

Модули используют общие глобальные данные.

### Сцепление по содержимому

Один модуль обращается к внутренним данным или коду другого в обход интерфейса.

Чем сильнее сцепление, тем труднее независимо изменять и тестировать модули.

# 4. Автоматическое построение лексических и синтаксических анализаторов

## 4.1. Общая схема

```text
регулярные выражения
        ↓
генератор лексера
        ↓
лексический анализатор

контекстно-свободная грамматика
        ↓
генератор парсера
        ↓
синтаксический анализатор
        ↓
дерево разбора или AST
```

Лексический анализ преобразует символы в токены, синтаксический — токены в структурное представление программы.



## 4.2. Генерация лексического анализатора

Лексические классы задаются регулярными выражениями:

```text
digit      = [0-9]
identifier = [A-Za-z_][A-Za-z0-9_]*
integer    = [0-9]+
```

Теоретическая схема:

\[
\text{регулярные выражения}
\to
\varepsilon\text{-НКА}
\to
\text{ДКА}
\to
\text{таблица переходов или код}.
\]

Этапы:

1. построить НКА для правил;
2. объединить автоматы;
3. детерминировать;
4. назначить действия принимающим состояниям;
5. при необходимости минимизировать автомат;
6. сгенерировать программный код.

При нескольких возможных распознаваниях обычно выбирается максимально длинная лексема, а при равной длине — правило с более высоким приоритетом.



## 4.3. Lex и Flex

Описание Flex содержит правила вида:

```text
регулярное выражение → действие на C
```

Структура файла:

```text
определения
%%
правила
%%
пользовательский код
```

Пример:

```lex
DIGIT [0-9]

%%
{DIGIT}+                     { return NUMBER; }
[A-Za-z_][A-Za-z0-9_]*       { return IDENTIFIER; }
"+"                          { return PLUS; }
[ \t\r\n]+                   { /* пропустить */ }
.                            { return ERROR; }
%%
```

Flex получает пары «регулярное выражение — C-код» и обычно генерирует файл `lex.yy.c` с функцией `yylex()`. При обнаружении шаблона выполняется связанное с ним действие. ([westes.github.io](https://westes.github.io/flex/manual/Introduction.html?utm_source=openai))

Дополнительные средства:

- начальные состояния;
- несколько входных буферов;
- отслеживание строк;
- повторно входимые анализаторы;
- передача атрибутов парсеру;
- генерация C- или C++-сканеров.

Начальные состояния полезны для строк, комментариев и других контекстов, в которых одинаковые символы имеют различный смысл.



## 4.4. Генерация синтаксического анализатора

Входом является контекстно-свободная грамматика:

\[
G=(N,\Sigma,P,S),
\]

где:

- \(N\) — нетерминалы;
- \(\Sigma\) — терминалы;
- \(P\) — продукции;
- \(S\) — начальный символ.

Пример:

\[
E\to E+T\mid T,
\]

\[
T\to T*F\mid F,
\]

\[
F\to(E)\mid id.
\]

К правилам могут добавляться:

- типы атрибутов;
- семантические действия;
- правила приоритетов;
- ассоциативность;
- действия восстановления после ошибок.



## 4.5. Yacc и Bison

Yacc — классический генератор восходящих анализаторов. GNU Bison является расширенной Yacc-совместимой системой.

Структура описания:

```text
объявления
%%
продукции
%%
пользовательский код
```

Пример:

```bison
%token NUMBER

%left '+'
%left '*'

%%
expr:
      expr '+' expr   { $$ = make_add($1, $3); }
    | expr '*' expr   { $$ = make_mul($1, $3); }
    | NUMBER          { $$ = make_number($1); }
    ;
%%
```

Здесь:

- `$1`, `$3` — значения символов правой части;
- `$$` — значение левой части;
- семантические действия создают узлы дерева.

Традиционные Yacc-анализаторы относятся к классу LALR(1). Bison дополнительно поддерживает IELR, канонический LR и GLR-разбор. ([gnu.org](https://www.gnu.org/software/bison/manual/html_node/Bison.html?utm_source=openai))



## 4.6. Работа LR-анализатора

LR-парсер использует:

- стек состояний;
- таблицу `ACTION`;
- таблицу `GOTO`;
- один или несколько символов предпросмотра.

Основные действия:

### Shift

Прочитать токен и поместить новое состояние в стек.

### Reduce

Заменить правую часть продукции её левой частью.

### Accept

Успешно завершить разбор.

### Error

Зафиксировать синтаксическую ошибку и попытаться восстановить разбор.



## 4.7. Конфликты

### Shift/reduce

Неясно, следует ли прочитать новый токен или выполнить свёртку.

### Reduce/reduce

Неясно, какую из двух продукций следует свернуть.

Причины конфликтов:

- неоднозначная грамматика;
- ошибка в грамматике;
- недостаточная мощность выбранного метода;
- отсутствие правил приоритетов.

GLR-анализатор при неразрешённом конфликте может вести несколько вариантов разбора и отбрасывать неуспешные. ([gnu.org](https://www.gnu.org/software/bison/manual/html_node/GLR-Parsers.html?utm_source=openai))



## 4.8. Взаимодействие лексера и парсера

```text
символы
   ↓
yylex()
   ↓
токен + семантическое значение + координаты
   ↓
yyparse()
   ↓
дерево разбора или AST
```

Например:

```text
"123" → NUMBER, value=123
```

Парсер использует:

- категорию `NUMBER` для выбора правила;
- значение `123` для построения узла;
- координаты для диагностики.



## 4.9. Дерево разбора и AST

**Дерево разбора** полностью отражает продукционные правила грамматики.

**Абстрактное синтаксическое дерево**, AST, сохраняет только семантически существенные элементы.

Для:

```text
a + b * c
```

AST имеет вид:

```text
       +
      / \
     a   *
        / \
       b   c
```

Служебные нетерминалы, скобки и разделители в AST обычно отсутствуют.



## 4.10. ANTLR

ANTLR — генератор лексеров, парсеров и инструментов обхода дерева.

Пример:

```antlr
grammar Expr;

prog : expr EOF ;

expr
    : expr '*' expr
    | expr '+' expr
    | INT
    | '(' expr ')'
    ;

INT : [0-9]+;
WS  : [ \t\r\n]+ -> skip;
```

ANTLR по грамматике генерирует парсер, способный строить дерево разбора и предоставлять средства его обхода. ([antlr.org](https://www.antlr.org/?utm_source=openai))

### Listener

Методы вызываются при входе и выходе из узлов:

```text
enterExpr
exitExpr
```

### Visitor

Клиент явно обходит дерево и получает возвращаемые значения:

```text
visitExpr(node)
```

Listener удобен для событийной обработки, visitor — для вычисления результата или построения собственного AST.

Современная линия ANTLR использует адаптивный нисходящий анализ, который принимает решение на основании фактического контекста разбора. ([antlr.org](https://www.antlr.org/papers/allstar-techreport.pdf?utm_source=openai))



## 4.11. Парсер-комбинаторы

**Парсер-комбинатор** — функция или объект-парсер, который строится композицией более простых парсеров.

Упрощённо:

\[
Parser(A):Input\to Result(A,Input).
\]

Базовые парсеры распознают:

- символ;
- строку;
- класс символов;
- токен.

Комбинаторы:

- последовательность;
- альтернатива;
- повторение;
- необязательный элемент;
- преобразование результата;
- зависимый разбор.

Псевдокод:

```text
number =
    many1(digit).map(toInteger)

term =
    number
    or between("(", expression, ")")

expression =
    chainLeft(term, "+", makeAddition)
```

Классическая функциональная модель представляет парсер как функцию, принимающую вход и возвращающую результат разбора с непрочитанным остатком; сложные парсеры строятся комбинаторами над простыми. ([moss.cs.iit.edu](https://moss.cs.iit.edu/cs340/pearl.pdf?utm_source=openai))

### Достоинства

- грамматика описывается непосредственно на языке программирования;
- композиционность;
- типобезопасность;
- возможность обычной отладки;
- простое добавление семантики;
- не требуется отдельный генератор.

### Недостатки

- непосредственная левая рекурсия в простом рекурсивном спуске приводит к зацикливанию;
- неосторожный возврат может иметь экспоненциальную сложность;
- требуется управлять точками фиксации выбора;
- качество сообщений об ошибках зависит от библиотеки.



## 4.12. Сравнение инструментов

| Инструмент | Назначение | Формальная основа |
||||
| Lex/Flex | генерация сканера | регулярные выражения и автоматы |
| Yacc/Bison | восходящий парсер | LALR/LR/GLR |
| ANTLR | лексер, нисходящий парсер, деревья | адаптивный LL |
| Парсер-комбинаторы | парсер как композиция функций | рекурсивный спуск |

# 5. Системы сборки и управления модулями

## 5.1. Понятие сборки

**Сборка** — процесс получения готового программного продукта из исходных текстов и вспомогательных материалов.

Она может включать:

1. генерацию исходного кода;
2. компиляцию;
3. ассемблирование;
4. связывание;
5. копирование ресурсов;
6. статический анализ;
7. тестирование;
8. формирование документации;
9. упаковку;
10. подписание;
11. публикацию;
12. развёртывание.



## 5.2. Граф зависимостей

Сборка представляется ориентированным графом:

\[
G=(V,E),
\]

где вершины — исходные и производные артефакты, а ребро:

\[
u\to v
\]

означает, что для построения \(v\) требуется \(u\).

```text
main.c ──► main.o ──┐
                    ├──► application
util.c ──► util.o ──┘
```

Система сборки должна:

- найти требуемые цели;
- определить устаревшие зависимости;
- построить их в правильном порядке;
- параллельно выполнить независимые действия;
- остановить зависимые действия при ошибке.



## 5.3. Make

Основная конструкция Make:

```make
target: prerequisites
	recipe
```

Пример:

```make
CC = cc
CFLAGS = -Wall -O2

app: main.o util.o
	$(CC) -o $@ $^

main.o: main.c util.h
	$(CC) $(CFLAGS) -c main.c

util.o: util.c util.h
	$(CC) $(CFLAGS) -c util.c

.PHONY: clean

clean:
	rm -f app main.o util.o
```

Здесь:

- `target` — цель;
- `prerequisites` — зависимости;
- `recipe` — команды построения;
- `$@` — имя цели;
- `$^` — список зависимостей;
- `.PHONY` — цель, не соответствующая реальному файлу.

Make сначала считывает правила и строит граф целей, а затем определяет, какие цели требуется обновить. Обычная файловая цель считается устаревшей, если она отсутствует или одна из зависимостей новее неё. ([gnu.org](https://www.gnu.org/software/make/manual/make.html?utm_source=openai))

### Возможности Make

- явные правила;
- неявные и шаблонные правила;
- переменные;
- функции;
- условные конструкции;
- подключение других Makefile;
- автоматическая генерация зависимостей;
- параллельная сборка;
- выбор отдельной цели.

Пример шаблонного правила:

```make
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
```



## 5.4. Ограничения Make

1. Классический механизм основан преимущественно на временных метках.
2. Скрытые зависимости должны быть явно добавлены.
3. Поведение команд зависит от используемой оболочки.
4. Большие Makefile могут стать трудно сопровождаемыми.
5. Сам Make не разрешает версии сторонних пакетов.
6. Результат может зависеть от переменных окружения и установленных инструментов.

Make является системой выполнения правил, а не компилятором и не полноценным менеджером пакетов.



## 5.5. CMake

В формулировке билета CMake поставлен рядом с системами, ориентированными на конкретные языки, однако это требует уточнения:

> **CMake — кроссплатформенный генератор, или метасистема сборки, а не система только для одного языка.**

CMake формирует входные файлы для выбранной нативной системы: Make, Ninja, Visual Studio, Xcode и других. ([cmake.org](https://cmake.org/cmake/help/latest/manual/cmake-generators.7.html?utm_source=openai))

Пример:

```cmake
cmake_minimum_required(VERSION 3.20)

project(example LANGUAGES C)

add_library(util util.c)
add_executable(app main.c)

target_link_libraries(app PRIVATE util)
```

Запуск:

```sh
cmake -S . -B build
cmake --build build
```

Основные стадии:

1. **конфигурирование** — чтение проекта и проверка окружения;
2. **генерация** — создание файлов нативной системы сборки;
3. **собственно сборка** — запуск выбранного инструмента.

CMake оперирует целями:

- исполняемыми файлами;
- библиотеками;
- пользовательскими командами.

Зависимости между двоичными целями задаются, в частности, через `target_link_libraries`. ([cmake.org](https://cmake.org/cmake/help/v3.30/manual/cmake-buildsystem.7.html?utm_source=openai))



## 5.6. Cargo

Cargo — система сборки и менеджер пакетов экосистемы Rust.

Файл проекта:

```text
Cargo.toml
```

Пример:

```toml
[package]
name = "example"
version = "0.1.0"
edition = "2024"

[dependencies]
serde = "1"
```

Основные команды:

```sh
cargo build
cargo run
cargo test
cargo check
cargo doc
cargo publish
```

Понятия:

- **crate** — единица компиляции Rust;
- **package** — распространяемая единица из одного или нескольких crates;
- **workspace** — набор совместно управляемых пакетов.

`Cargo.toml` задаёт допустимые зависимости и метаданные пакета, а `Cargo.lock` сохраняет точные разрешённые версии и ревизии. ([doc.rust-lang.org](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html?utm_source=openai))



## 5.7. Maven

Maven ориентирован прежде всего на Java и другие языки JVM.

Проект описывается файлом:

```text
pom.xml
```

Основные координаты артефакта:

\[
groupId:artifactId:version.
\]

Пример:

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>org.example</groupId>
    <artifactId>application</artifactId>
    <version>1.0.0</version>
</project>
```

Основные фазы жизненного цикла:

1. `validate`;
2. `compile`;
3. `test`;
4. `package`;
5. `verify`;
6. `install`;
7. `deploy`.

При вызове поздней фазы выполняются необходимые предшествующие фазы. Maven имеет встроенные жизненные циклы `default`, `clean` и `site`; конкретные действия выполняются плагинами. ([maven.apache.org](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html?utm_source=openai))



## 5.8. Зависимости Maven

```xml
<dependency>
    <groupId>org.example</groupId>
    <artifactId>library</artifactId>
    <version>1.2.0</version>
</dependency>
```

Maven поддерживает:

- транзитивные зависимости;
- области видимости;
- исключения;
- необязательные зависимости;
- `dependencyManagement`;
- BOM;
- локальные и удалённые репозитории.

При конфликте транзитивных версий Maven обычно выбирает ближайшее определение в дереве зависимостей, если версия не зафиксирована явно через управление зависимостями. ([maven.apache.org](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html?utm_source=openai))



## 5.9. Модули, пакеты и артефакты

Необходимо различать:

- **модуль** — логическая единица исходной программы;
- **единицу компиляции** — вход компилятора;
- **пакет** — единицу распространения;
- **библиотеку** — повторно используемый код;
- **артефакт** — результат сборки;
- **репозиторий пакетов** — хранилище версий;
- **lock-файл** — фиксацию выбранного графа зависимостей.

Менеджер пакетов решает задачи:

1. описания пакета;
2. разрешения версий;
3. загрузки;
4. проверки целостности;
5. установки;
6. публикации;
7. обновления;
8. удаления.



## 5.10. Воспроизводимость сборки

Для воспроизводимости требуется контролировать:

- версии исходного кода;
- точные версии зависимостей;
- версию компилятора;
- системные библиотеки;
- параметры сборки;
- переменные окружения;
- генераторы кода;
- базовую операционную среду;
- временные и случайные данные.

Lock-файл фиксирует граф библиотечных зависимостей, но не гарантирует побитовую воспроизводимость, если не зафиксированы компилятор и окружение.

# 6. Конфигурационное управление, VCS, Git и CI/CD

## 6.1. Конфигурационное управление

**Конфигурационное управление программным обеспечением**, SCM, — дисциплина идентификации, контролируемого изменения, учёта состояния и проверки целостности программного продукта на протяжении жизненного цикла.

Конфигурационными единицами могут быть:

- требования;
- исходный код;
- архитектурные модели;
- тесты;
- сценарии сборки;
- схемы БД;
- конфигурационные файлы;
- документация;
- библиотеки;
- контейнерные образы;
- исполняемые файлы;
- параметры развёртывания.

К основным процессам SCM относятся идентификация конфигурации, управление изменениями, учёт состояния, аудит, сборка, управление выпусками и доставкой. ([swebokwiki.org](https://swebokwiki.org/Chapter_6%3A_Software_Configuration_Management?utm_source=openai))



## 6.2. Основные процессы SCM

### Идентификация

Определяются:

- контролируемые элементы;
- правила именования;
- версии;
- связи между элементами;
- базовые линии.

### Базовая линия

**Baseline** — согласованная и зафиксированная конфигурация, изменяемая только по установленной процедуре.

### Контроль изменений

1. зарегистрировать запрос;
2. оценить влияние;
3. одобрить или отклонить;
4. реализовать;
5. проверить;
6. включить в новую конфигурацию.

### Учёт состояния

Отслеживается:

- какие версии существуют;
- какие изменения утверждены;
- какие дефекты исправлены;
- что вошло в конкретную сборку.

### Аудит

Проверяется:

- соответствие продукта описанию;
- полнота утверждённых изменений;
- отсутствие несанкционированных изменений;
- воспроизводимость выпуска.

### Управление выпуском

Включает идентификацию, упаковку и доставку программы, документации, конфигурационных данных и сопутствующих материалов.



## 6.3. Система управления версиями

**Система управления версиями**, VCS, записывает изменения файлов и позволяет:

- вернуться к прежней версии;
- сравнить состояния;
- определить автора изменения;
- создать ветку;
- объединить изменения;
- пометить выпуск;
- организовать совместную работу.

VCS — важная часть SCM, но не всё конфигурационное управление: сама по себе она не определяет процесс утверждения изменений, аудит и правила выпуска.



## 6.4. Централизованные VCS

В централизованной системе основной репозиторий хранится на сервере:

```text
клиент A ─┐
клиент B ─┼── центральный репозиторий
клиент C ─┘
```

Примеры:

- CVS;
- Subversion;
- централизованные режимы корпоративных систем.

### Достоинства

- единая точка управления;
- простая модель прав;
- единая последовательность ревизий;
- централизованное резервное копирование.

### Недостатки

- зависимость от сервера;
- ограниченная автономная работа;
- сервер может стать единой точкой отказа;
- многие операции требуют сети.



## 6.5. Распределённые VCS

В распределённой системе обычный полный клон содержит рабочую историю репозитория:

```text
локальный репозиторий A ⇄ удалённый репозиторий
локальный репозиторий B ⇄ удалённый репозиторий
```

Примеры:

- Git;
- Mercurial.

### Достоинства

- локальные коммиты;
- большинство операций не требует сети;
- быстрые ветвления и просмотр истории;
- несколько удалённых репозиториев;
- гибкие схемы сотрудничества.

В распределённой VCS клиенты получают не только текущую копию файлов, но и репозиторий с историей, что позволяет выполнять основные операции локально. ([git-scm.com](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control.html?utm_source=openai))



## 6.6. Внутренняя модель Git

Git рассматривает состояние проекта как снимки.

Основные объекты:

- **blob** — содержимое файла;
- **tree** — структура каталога;
- **commit** — ссылка на дерево, родительские коммиты и метаданные;
- **tag** — именованная ссылка или отдельный объект тега.

Коммит содержит ссылку на снимок подготовленных данных и на родительский коммит или коммиты. Ветка представляет собой перемещаемый указатель на коммит. ([git-scm.com](https://git-scm.com/book/ru/v2/%D0%92%D0%B5%D1%82%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5-%D0%B2-Git-%D0%9E-%D0%B2%D0%B5%D1%82%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B8-%D0%B2-%D0%B4%D0%B2%D1%83%D1%85-%D1%81%D0%BB%D0%BE%D0%B2%D0%B0%D1%85?utm_source=openai))

Основные области:

```text
рабочее дерево
      ↓ git add
индекс
      ↓ git commit
локальный репозиторий
      ↓ git push
удалённый репозиторий
```

Файл может быть:

- изменённым;
- добавленным в индекс;
- зафиксированным.

Эти состояния и соответствующие им рабочее дерево, индекс и каталог Git являются основой локального процесса. ([git-scm.com](https://git-scm.com/book/ru/v2/%D0%92%D0%B2%D0%B5%D0%B4%D0%B5%D0%BD%D0%B8%D0%B5-%D0%A7%D1%82%D0%BE-%D1%82%D0%B0%D0%BA%D0%BE%D0%B5-Git%3F?utm_source=openai))



## 6.7. Основные команды Git

```sh
git clone
git status
git add
git commit
git branch
git switch
git merge
git rebase
git fetch
git pull
git push
git tag
git revert
```

### `fetch`

Получает данные из удалённого репозитория, но не обязан изменять текущую ветку.

### `pull`

Обычно сочетает получение данных с их интеграцией в текущую ветку.

### `merge`

Объединяет линии разработки, при необходимости создавая коммит слияния.

### `rebase`

Повторно применяет коммиты одной линии поверх другой, переписывая их родительские связи и идентификаторы.

Merge сохраняет структуру параллельной истории, а rebase формирует более линейную историю. Перебазирование не следует без согласования применять к уже опубликованным коммитам, на которых основана чужая работа. ([git-scm.com](https://git-scm.com/book/id/v2/Git-Branching-Rebasing?utm_source=openai))



## 6.8. Рабочие процессы Git

Термин **Git workflow** не означает единственный обязательный процесс. Распределённая модель позволяет применять разные схемы:

- централизованный процесс с одним общим репозиторием;
- короткоживущие функциональные ветви;
- работу через форки;
- процесс с диспетчером интеграции;
- иерархическую схему с несколькими интеграторами;
- разработку непосредственно около основной ветви.

Pro Git описывает, в частности, централизованный процесс, процесс диспетчера интеграции и иерархический процесс «диктатор и помощники». ([git-scm.com](https://git-scm.com/book/ru/v2/%D0%A0%D0%B0%D1%81%D0%BF%D1%80%D0%B5%D0%B4%D0%B5%D0%BB%D1%91%D0%BD%D0%BD%D1%8B%D0%B9-Git-%D0%A0%D0%B0%D1%81%D0%BF%D1%80%D0%B5%D0%B4%D0%B5%D0%BB%D1%91%D0%BD%D0%BD%D1%8B%D0%B9-%D1%80%D0%B0%D0%B1%D0%BE%D1%87%D0%B8%D0%B9-%D0%BF%D1%80%D0%BE%D1%86%D0%B5%D1%81%D1%81?utm_source=openai))

Типовой процесс команды:

1. зарегистрировать задачу;
2. создать ветку от актуальной основной ветви;
3. внести небольшие логически завершённые изменения;
4. создать коммиты;
5. получить изменения основной ветви;
6. разрешить конфликты;
7. отправить ветку;
8. создать запрос на слияние;
9. пройти CI и review;
10. объединить изменения;
11. удалить временную ветку;
12. пометить выпуск тегом при необходимости.



## 6.9. Git Flow как специальная модель

Если в формулировке экзамена под **Git Workflow** подразумевается именно **Git Flow**, следует описать модель с ветвями:

- `main` — выпущенные версии;
- `develop` — интеграция следующего выпуска;
- `feature/*` — разработка функций;
- `release/*` — подготовка выпуска;
- `hotfix/*` — срочные исправления.

```text
feature ──► develop ──► release ──► main
               ▲           │
               └───────────┘

main ──► hotfix ──► main и develop
```

Git Flow подходит для проектов:

- с плановыми выпусками;
- длительной стабилизацией;
- сопровождением нескольких версий.

Недостатки:

- долгоживущие ветви;
- поздняя интеграция;
- сложные слияния;
- избыточность для непрерывного развёртывания.

Важно: Git Flow — не встроенное требование Git, а одна из возможных моделей ветвления.



## 6.10. GitHub Flow

**GitHub flow** — лёгкий процесс на основе короткоживущих ветвей и pull request.

Основная последовательность:

1. создать ветку от основной;
2. внести изменения;
3. делать коммиты;
4. отправить ветку в GitHub;
5. открыть pull request;
6. провести обсуждение и review;
7. выполнить автоматические проверки;
8. исправить замечания;
9. объединить pull request;
10. удалить ветку;
11. выпустить или развернуть изменение.

GitHub официально определяет GitHub flow как лёгкий процесс на основе ветвей. ([docs.github.com](https://docs.github.com/en/get-started/using-github/github-flow?ref=marketsplash&utm_source=openai))

### Pull request

Pull request является средством:

- предложить изменение;
- обсудить реализацию;
- показать разницу;
- выполнить review;
- запустить проверки;
- зафиксировать решение об интеграции.

Основная ветка обычно защищается правилами, запрещающими непосредственное изменение без проверок и одобрения.



## 6.11. Непрерывная интеграция

**Continuous Integration, CI** — практика частого объединения изменений с автоматической проверкой каждого изменения.

Типичный конвейер:

```text
commit или pull request
          ↓
получение исходного кода
          ↓
установка зависимостей
          ↓
сборка
          ↓
статический анализ
          ↓
модульные тесты
          ↓
интеграционные тесты
          ↓
формирование артефакта
```

CI позволяет рано выявлять:

- ошибки компиляции;
- конфликты интеграции;
- регрессии;
- нарушение стиля;
- дефекты тестов;
- известные уязвимости зависимостей.

GitHub Actions, например, позволяет автоматически запускать сборку и тестирование pull request, а также выполнять развёртывание после интеграции. ([docs.github.com](https://docs.github.com/en/actions/get-started/understand-github-actions?learn=getting_started&utm_source=openai))



## 6.12. Continuous Delivery и Continuous Deployment

### Continuous Delivery

Каждое изменение, прошедшее проверки, автоматически подготавливается к выпуску. Решение о развёртывании в производственную среду может приниматься вручную.

### Continuous Deployment

Каждое изменение, прошедшее все проверки, автоматически развёртывается в production.

Следовательно, нужно различать:

- **CI** — автоматическую интеграционную проверку;
- **delivery** — постоянную техническую готовность к выпуску;
- **deployment** — автоматический выпуск в рабочую среду.

GitHub определяет continuous deployment как автоматизированную публикацию и развёртывание обновлений после их сборки и тестирования. ([docs.github.com](https://docs.github.com/en/actions/get-started/continuous-deployment?utm_source=openai))



## 6.13. Элементы CI/CD-системы

### Workflow

Описание конвейера, обычно хранимое вместе с кодом.

### Trigger

Событие запуска:

- push;
- pull request;
- тег;
- расписание;
- ручной запуск;
- внешний запрос.

### Job

Относительно самостоятельная часть процесса.

### Step

Отдельная команда или действие внутри job.

### Runner или agent

Машина или контейнер, выполняющие job.

### Artifact

Результат сборки:

- исполняемый файл;
- библиотека;
- пакет;
- контейнерный образ;
- отчёт;
- документация.

### Cache

Повторно используемые промежуточные данные, например загруженные зависимости. Кэш не следует смешивать с артефактом выпуска.

### Environment

Целевая среда:

- development;
- testing;
- staging;
- production.

### Secret

Защищённое значение: токен, ключ или пароль.



## 6.14. Пример CI-конвейера

```yaml
name: CI

on:
  pull_request:
  push:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Build
        run: make

      - name: Test
        run: make test
```

Для производственного развёртывания применяются:

- защищённые environments;
- обязательные одобрения;
- ограничения ветвей;
- секреты среды;
- запрет одновременных развёртываний;
- журнал истории выпусков.

GitHub Actions предоставляет environments, правила защиты и группы конкурентности, позволяющие ограничить одновременное развёртывание и потребовать одобрение перед production. ([docs.github.com](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments?utm_source=openai))



## 6.15. Требования к надёжному CI/CD

1. Исходный код и конфигурация конвейера должны версионироваться.
2. Сборка должна быть воспроизводимой.
3. Зависимости должны иметь контролируемые версии.
4. Секреты нельзя хранить в исходном коде.
5. Один и тот же артефакт должен продвигаться между средами.
6. Ручные изменения production должны быть минимизированы.
7. Необходимы журналирование и аудит.
8. Должна существовать процедура отката.
9. Развёртывание должно включать проверку работоспособности.
10. Права конвейера должны соответствовать принципу минимальных привилегий.
